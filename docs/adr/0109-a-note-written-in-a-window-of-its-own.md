# 0109 — A note written in a window of its own

Date: 2026-11-16. Status: built on 2026-11-16, its choices not yet confirmed by the owner, and tried in the running application the same day (see the end); from the owner's words of the same day ("I would like to have an executable that opens a note window in which I can write whatever. When I submit it, it goes to the notebook. It would be great if it works also when the main Glaukopis app is closed."), and, after the plan was written, "Let it be possible to format in the note window, and also to add pictures. Perhaps also other files, what do you think?" and "It should be possible to make lists also." Stands on 0101 and 0102: the note goes into the notebook's inbox, which the application already takes in. Amends 0102 (the inbox is no longer the plugin's alone). The plan: `docs/plans/the-chat-answered-set-marked-and-changed-and-a-paragraph-made-an-element.md`, part F, with what the owner said after it written into the decisions below.

## Context

- **The notebook has an inbox** (0102), `notebook/inbox/` in the data folder: the helper Firefox starts, which is the application itself in another role, writes each thing whole into it without the application running; the application looks at it at its start and every second and a half while it runs, and makes notes of what it holds.
- **The application already starts itself in other roles**, decided first thing in `main`: the helper of the plugin, and the child that reads a PDF (`--glaukopis-isolated`).
- **Started again while it runs**, Glaukopis opens a new window of the one that runs (0085, `tauri_plugin_single_instance`); a second Glaukopis in the same data folder finds it claimed and says so.
- **A note of the notebook is a text of the body schema** (0101), written with the text's own editor and its holder (0100): marks, the kinds of paragraph with the lists among them, pictures as figures and files by their names.
- **WebKitGTK ends the program at a paste from an empty clipboard** (0048), and its new compositor flickers on some desktops (0049): the application reads pastes through GTK and asks for the older compositor.

## Decision

1. **`glaukopis --note` opens one small window and nothing else of the application**: no project, no library and no notebook is opened by it, no folder is moved or claimed, nothing of the settings is written. It works while Glaukopis runs and while it does not, beside it and never through it: it takes no part in the single instance, and a second `--note` opens a second window. The flag is taken in `main.rs` as the other roles are; a function beside `run()`, `run_note_window()`, builds the small application: the data folder found as `run()` finds it, nothing moved; the log on the standard error and in no file; one window labelled `note`; only the commands it needs. The page (`src/main.ts`) mounts a page of its own in that window instead of `App.svelte`, told by the window's label, and each page is loaded only where it is shown.
2. **The window**: about 480 by 320, resizable, its title the word for a note. The field is **the text's own editor** (`editor/RichText.svelte`) over the body schema, as the notebook's notes have it, with a holder of its own beside the project's and the notebook's: its marks, its kinds of paragraph with the lists among them (bulleted, numbered, to tick), its keys, what is typed at the start of a line (`- `, `1. `, `[ ] `, `> `), its undo and its pasting are the text's own, under the same keys everywhere. The holder cites nothing, has no comments and no words to pass over; spelling is off in the window.
3. **Under the field one row**, as the chat's field has: buttons for bold, italic, underlined, struck through and code (the text's words and keys for them), three buttons for the kinds of list, **Add a file…** (a paperclip), and at the right **To the notebook**.
4. **Pictures and other files come in three ways**: pasted (a picture on the clipboard, a screenshot above all; files copied in a file manager, on Linux through the paste of 0048), dropped on the window from a file manager, and by **Add a file…**, the system's dialog, several at once. A picture stands in the note as a picture where it is put; any other file as the notebook shows a file a note holds, by its name. A file is copied, at most 50 MB each (the inbox's limit for a picture, which is now the limit for a file); a larger one is not taken, and that is said.
5. **Ctrl+S sends**, as the button does (Ctrl+Enter ticks a point of a list to tick, as in every text). **Escape** closes the window where the note is empty, and does nothing where it is not. Nothing is sent of an empty note: no words, and no file.
6. **What is written and not sent is kept, its pictures and files with it** (the thought of 0094): in a folder of the notebook's folder in the data, `notebook/unsent-notes/<id>/`, beside `inbox/`: the text as it is, written whole a moment after each change and before the window closes, and each file as it is added, named by what it holds. The window opens with it; it goes when the note is sent or emptied. Closed with a note in it, by its own × or the system, the window loses nothing.
7. **Sent**, the note goes into the inbox whole or not at all, as a thing of a new kind, `note`, with when: its text as ProseMirror's JSON of the body schema, its plain words beside it for whatever cannot read that, and the files it holds beside `item.json`, moved there from the folder of the note not sent (the same disk, a rename; moved back where the note cannot be put), each named in `item.json`. The limits of the inbox hold: the text by its bytes, each file by its size, a name by its length. Then the window closes and the process ends; where the note cannot be written, the window stays, with its note, and says so.
8. **The application takes it in** as it takes what the plugin hands over: a note without a name and with no source. Its text is read with care: only what the window makes is kept (paragraphs of every kind, line breaks, the marks of words, links that may be followed, pictures, files); a citation, a note, a formula, a cross-reference, a table and the like are left out; what cannot be read at all gives a paragraph for each line of the plain words, and then its pictures and files. Each file is taken into the store as the notebook's, as files dropped into the notebook are, and the pictures and files of the text point to what was stored (by the hash the window named each by, which is the store's; a picture to what a figure shows of it). What the application says of things taken from the inbox is true of a note too: *Added to the notebook*, with **Show**.
9. **The window speaks the language of the settings and has their look** (the theme, the colours of one's own, the size of the interface and of the text, the font of the text): read, never written. On Linux the page stops pastes and has them read through GTK as the application does, and the web view gets the same environment (the compositor of 0049); the code is shared, not copied.
10. **The core**: the new kind in `inbox::Kind`, written through the inbox's own writing with its limits (`put_note`); the note not sent, its files, and the finding of the data folder in `notebook/note_window.rs`. The helper of the plugin refuses the kind `note`, and drops a text and files of a note from what the plugin sends.
11. **Names**: the commands (`note_window_…`), the file of the commands (`commands/notewindow.rs`) and `src/lib/api/notewindow.ts` are named for what the thing is, a note written in a window of its own.
12. **The Linux packages**: a command **`glaukopis-note`**, a script of two lines in `packaging/linux/` that starts `glaukopis --note`, installed beside `glaukopis` by both Arch recipes, and by the deb and the rpm through the files the bundler's configuration places; and an action **New note** (*Nytt notat*) on the desktop file of the Arch package, so that the launcher offers it.
13. **Windows and macOS** get no program of their own: the same flag, `glaukopis.exe --note`, and on macOS `open -n -a Glaukopis --args --note`. The guide says so, and that a key of the desktop can be bound to it.

## Choices made in building this, which the owner has not been asked about

1. **The application in another role rather than a second program; Escape that does nothing where something is written; a second window where it is started twice; the names of the command, the button and the action** (those of the plan).
2. **`--note` is taken wherever it stands among the arguments**, not only first, since macOS's `open --args` may put something of its own before it.
3. **The data folder**: the one `GLAUKOPIS_DATA_DIR` names, else the folder the writer chose (while a move is under way, the folder moved from, while it is there), else the usual one. A chosen folder that is not there, its disk unplugged, is not made: the window opens, and says, when it cannot keep or send, that the folder is not found. The usual folder is made where Glaukopis was never started, when the first note is kept, as the application itself would make it.
4. **The window has no library**: a figure in it shows its picture from the folder of the note, and the panel of a figure finds no files of the library to offer as versions. A file in the note is not opened from the window.
5. **What a figure shows as it is (PNG, JPEG, SVG) stands as a picture**; any other image (a TIFF, a WebP, a GIF) stands as a file, by its name, and is a file in the notebook too.
6. **A paste of words with a picture beside them**, as when something is copied from a page, is the words, as in every text; a picture alone on the clipboard, and files copied in a file manager, are pictures and files. To have the files, the clipboard of Linux now says the other files copied in a file manager by their paths (`Pasted.files`); the application's other texts make nothing of them.
7. **The keys of what the window does not make are not taken** in it: Ctrl+Alt+F (a note), M and E (formulas), R (a cross-reference), K (a mark of a place), T (a table). Ctrl+Alt+P chooses a picture, as in every text. What is pasted that the window does not make (a table in HTML, say) stands in the window, and is left out when the application takes the note in.
8. **Each window claims a folder of its own for its note not sent** (`<id>.in-use`, locked while it is open, as the data folder is claimed), so that two windows open at once never write into one; a window opened takes the oldest note not sent that no other window has, and a second window opened beside it begins empty. An emptied note loses its text at once and its files when a window next takes the folder, so that a file being added while the note is empty is not taken from under it.
9. **The own words of the writer** (0035) are not laid over the window's: it speaks the built-in words of the language chosen.
10. **The window keeps the note 0.4 seconds after a change**, and before it closes; a keeping that fails while it closes keeps it open and says so, and a second closing closes it, as the application's windows do.
11. **Ctrl+S is in the sheet of keys**, under the notebook, as the window's own.
12. **The desktop action is on the Arch package's desktop file only**: the deb and the rpm have the desktop file Tauri writes, which has no actions; they have the command.

## Not done

- No citing, no notes at the foot, no formulas, no tables in the window; no name, no box and no tag for the note there: the notebook has all of that once the note is in it. No choosing of emojis, which writes the settings.
- No key of the system bound by Glaukopis itself: that is the desktop's.
- Not tried: the deb and the rpm with the command placed, and the Arch package with the command and the action (no package was built); files dropped on the window from a file manager, and a picture pasted from the clipboard of a desktop, which the scripts cannot do; Windows and macOS.

## Addendum, 2026-11-19: the menus of a text, the highlighter, and Clear the note

On the owner's words: "There is no highlight in the stand alone note window. In the rich text the icons are there, but they don't do anything", and "Could you also make a clear current note button for the standalone window?"

- **The window had nothing to show a menu in, nor a question.** It is a page of its own, mounted in the place of the application's, and was given the toasts and not the host of menus or of what is asked before something is taken away. So on a sheet of rich text there (0112) every tool that opens a menu did nothing: the colour of the words, the highlighter, the menu of the sheet, *More tools*; and *Make it ordinary text* waited for an answer to a question that was never shown. The buttons that act at once worked. The window now has both hosts (`MenuHost`, `ConfirmHost`).
- **The script had not tried them**: it put a sheet in and left it, and pressed no tool of its head. It does now.
- **The highlighter is in the row** (0116), after the lists: its colours, and Ctrl+Alt+H as in every text.
- **Clear the note**, an eraser beside *To the notebook*: takes away everything written, in one step of undo of its own, so that undo brings back the note and nothing done just before the clearing is undone with it. Not asked about, since undo takes it back. Dimmed while the note is empty. What is kept of the note follows, as after any change: a cleared note is not there the next time the window opens.
- **Choices not asked about**: the eraser as its sign, and its place; that it does not ask.
- **Checked**: `e2e/note-window.mjs` (54 checks): the highlighter in the row, its colours, a colour set; the menu of a sheet opening; the highlighter of the sheet, in its row or under *More tools*; Clear the note leaving nothing to send, undo bringing back the words and both highlights. Looked at.
